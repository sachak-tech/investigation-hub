# Investigation Hub: current implementation handoff

Updated 12 November 2026. This is a code-state handoff, not a claim that the enterprise platform is complete. Verify against code and tests after each change.

## Product intent

Build a bank-configurable, agentic financial-crime investigation hub. Alerts may create or join a case within a policy-defined window; combinations can change case type and required investigation steps. Review layers and actions are bank-policy driven, not hardcoded to L1/L2/L3. Investigators should review agent work, navigate from a step to the relevant data section, and eventually use bank-configured external API sections. The target UI is Next.js.

## Implemented now

The executable platform is under [`Backend Projects/platform`](<../Backend Projects/platform>). It has four Java 25 / Spring Boot 4.1.2 services: Alert (18084), Policy (18081), Case (18082), and Playbook (18083), plus a Python 3.13/FastAPI Agent service (18085). Java services own PostgreSQL schemas and Flyway migrations; Agent owns `investigation_agent` with its SQL migration. All have API documentation. `service-common` is a library, not a service. Local outbox relays use HTTP; Kafka is not wired. See the [platform README](<../Backend Projects/platform/README.md>) for endpoints and commands.

- Alert ingestion is idempotent by tenant, source system, and source alert ID. Verified-subject alerts are delivered to Case.
- Policy deterministically chooses a case type and required/optional step IDs. Three synthetic tenants are seeded from JSON fixtures. Development-only draft, simulation, and publication endpoints now support additional JSON policies; [the dynamic policy scenario](<../Backend Projects/platform/dynamic_policy_scenario.py>) proves v1-to-v2 publication. Readable policy text exists for two fixtures, but text extraction, human approval, and authenticated tenant administration are not implemented.
- Case groups matching alerts, changes classification/required steps on a new alert, tracks revision, and exposes policy-permitted `ESCALATE`, `RETURN_FOR_REWORK`, and `APPROVE_CLOSE` actions. A closure gate checks the current required playbook steps and the pinned policy's approval stage. The development identity is a caller-supplied `X-Actor-Id` header, not real authentication.
- Case review stages and transitions are implemented in Case service from policy `reviewStages`; **there is no case-level BPMN/CMMN file**. The accepted route and alert/classification history are in the durable `case_journey_event` table and `GET /v1/cases/{caseId}/journey`.
- Playbook uses Flowable CMMN from [`investigation.cmmn`](<../Backend Projects/platform/playbook-service/src/main/resources/cases/investigation.cmmn>). Its shared model contains eight predefined step definitions. Policy-required steps activate at runtime, including linked and parallel steps. New **human** steps are injected from a generic [extension model](<../Backend Projects/platform/playbook-service/src/main/resources/cases/policy-extension.cmmn>) and mapped to product step IDs. Optional steps activate but do not block closure. Closing Case eventually closes the Flowable instance via the local relay.
- Read-only development views: [case journey](http://localhost:18082/case-journey.html) and [playbook monitor](http://localhost:18083/playbook-monitor.html). The playbook monitor distinguishes required steps from unrelated model items; Flowable's `terminated` state on unused items does not mean those tasks were completed.
- Step navigation is implemented in Playbook at `GET /v1/playbooks/cases/{caseId}/navigation` and `/steps/{stepId}/navigation`. It resolves the pinned policy's selected steps, destination, focus, case/customer context, data points, evidence requirements, and future workspace route. Policy-scoped `destinations` configure new mappings; a compatibility catalog covers original seeded destinations. The monitor links to a read-only section preview. Unselected steps return 404, unknown destinations are unavailable, and reconciliation mismatches return 409.
- Evidence-backed human task completion now uses `POST /v1/cases/{caseId}/steps/{stepId}/complete`. Case holds its row lock while Playbook validates a submission and commits the findings, source citations, immutable receipt, Flowable task completion, revision increment, and `StepCompleted` outbox event in one Playbook transaction. Supplied text is registered with a SHA-256 in `investigation_document`; citations must match exact document lines in the same case. The policy's completion evidence types, selected step, active task, stage action, revisions and existing task assignee are enforced. Receipts are available through `GET /v1/playbooks/cases/{caseId}/completions` and the read-only step preview. This is not an AI investigator or document authenticity/semantic validation.
- External data sections are deferred by user request. `EXTERNAL_SECTION` and `externalSectionRef` remain reserved navigation fields, returning unavailable without external API calls. Later work should add a connector and renderer behind this same contract; do not build external data retrieval as part of navigation alone.
- The first actual AI agent is implemented: [Bank Document Review Agent](<../Backend Projects/platform/agent-service/README.md>) using local Ollama (`qwen3:4b` for the verified synthetic proof). It reads supplied case text and pinned step requirements, produces cited findings/gaps, checks citation traceability, and derives readiness from gaps and required evidence coverage. Its PostgreSQL queue persists run IDs, model digest, prompt version, context hash, failures and results. Agent-configured steps require human review: submission leaves the task open; human acceptance uses the existing completion transaction; return stores feedback for a fresh run. Direct task completion and agent self-acceptance are blocked for these steps. Feedback is prompt guidance within that case, not model-weight training.
- A separate [Flowable spike](<../Backend Projects/flowable-spike/README.md>) demonstrated dynamic step injection and a Python external worker. Human task injection is now integrated into the platform; the Python worker is still only in the spike.

## Verification

On macOS/Linux or Windows WSL, install Java 25, Maven, PostgreSQL, `psql`, `curl`, `rg`, `lsof`, and Python 3.9+. Provide a local PostgreSQL database/user with permission to create schemas. From `Backend Projects/platform`, set `IH_DB_PASSWORD` and run `bash scripts/run-local.sh --smoke`. This builds the modules, creates schemas, applies migrations, starts the four services, verifies Swagger and a transaction-plus-KYC case, and stops the services. Use `bash scripts/run-local.sh` to leave them running; run `python3 case_routing_scenarios.py` for routing/closure/journey and `python3 linked_scenarios.py` for dependent tasks. Demo results are written under ignored `.cache/`.

Successful local checks include the platform smoke test with the fifth service, evidence-backed task completion regression, JSON contract validation, eight Python source/output validation tests, a real Ollama agent scenario with return/rework, acceptance and insufficient-source blocking, and browser verification that a user can start a local agent run and see cited findings awaiting review. Earlier case routing and dynamic policy/navigation scenarios also passed. Re-run on the receiving machine. The runner requires PostgreSQL; Git contains migrations and synthetic fixtures, **not the local database rows or previously created case IDs**. Fresh demo cases will get new IDs.

Run `python3 task_completion_scenario.py` for evidence validation, concurrent request replay, stale revision rejection, case isolation, saved receipt inspection, closure and linked-task activation. It uses the new completion API rather than the synthetic demo completion endpoint. The task-completion schema and example are included in `contracts/` and `examples/`.

Start all five services with `IH_START_AGENT_SERVICE=true bash scripts/run-local.sh` after following the [Python/Ollama setup](<../Backend Projects/platform/agent-service/README.md>). `python3 agent_scenario.py` uses the real local model to verify cited findings, human rework feedback, acceptance, blocked direct completion/self-review/stale review, and insufficient-information blocking. `PYTHONPATH=agent-service ../../.cache/agent-venv/bin/python -m unittest discover -s agent-service/tests -v` checks source/citation validation without model calls. The step preview can start a run and accept or return findings using a development reviewer ID and a reason. This is a development UI, not Next.js.

## Known limits and next work

### Most recently proposed next build: Validation Agent (not implemented)

There is currently **one actual AI agent**, the Bank Document Review Agent. The next proposal discussed with the user is a separate Validation Agent that checks whether its findings are supported by the original supplied sources. The user has not yet asked to start implementing this next agent; confirm the task before coding if the next conversation only asks for status.

The proposed slice should:

- Read the original case documents, pinned policy requirements, and the Bank Document Review Agent's immutable findings and citations.
- Report unsupported claims, contradictory evidence and missing information, with source references for each issue. Keep citation/rule enforcement in the existing backend alongside model-based semantic checks.
- Persist a versioned validation report with model/prompt metadata and the input run/context identifiers. Define the report contract and state transitions before wiring them into execution.
- Use policy to route findings toward human review or rework. Preserve the current required human approval gate and prevent acceptance of stale findings. Do not introduce autonomous case closure.
- Evaluate supported, deliberately incorrect, contradictory and incomplete examples, including source instructions intended to mislead the agent. Record measured results and failures. A second model call, particularly using the same model, is not proof of independent correctness.

This validation report, its API, orchestration and evaluation suite do **not** exist yet. Current deterministic validation verifies selected steps, policy evidence categories, document identity/hash, exact quote/line ranges and completion authority checks; it does not establish semantic correctness or document authenticity. Reuse the Python agent service and review APIs where appropriate rather than assuming a second service is required. External data sections/retrieval, model training, authentication and CI/CD retain their previously documented scope and deferrals.

### Other pending work

1. Build the actual Next.js investigator workspace using the implemented navigation API. Step clicks and section resolution are proven in a development preview; investigation data rendering is pending. Keep external API sections, response validation, and card/table rendering deferred until the user requests them.
2. Add authenticated human/agent identity, tenant and stage membership, semantic evidence sign-off, service-to-service authorization, and protected internal endpoints. Current `X-Actor-Id`/`X-Tenant-Id` are unverified; the task API checks an existing assignee and current stage action but not authenticated membership. The local demo completion endpoint is intentionally synthetic. Public completion holds the Case row lock during the normal Playbook call; distributed crash/timeout fencing and projection of `StepCompleted` into the Case timeline are still pending.
3. Extend the bounded first agent with broader evaluation, error recovery, additional policy-approved tools and agent types. Model quality, prompt injection robustness and domain correctness need a much larger reviewed evaluation set before bank use. The local synthetic proof is not a production-quality claim. Automatic Flowable job acquisition, document retrieval, autonomous closure and model training are not implemented. Queue leases support recovery, but process-loss and multiworker load testing remain pending.
4. Implement text policy intake, structured draft review, human approval, publishing authority, and migration rules for in-flight cases. JSON draft/simulate/publish exists only behind a development flag. New alerts after publication currently join only open cases pinned to the same policy version; another version creates a new case.
5. `reviewStages[].actionTargets` is supported for new policies. Legacy seeded fixtures still use stage-level `nextStages`; where a legacy stage allows two route actions, both actions can target every listed next stage. Migrate these fixtures to explicit action targets in a new policy version.
6. Required and optional steps are supported. Unselected CMMN model items are **not** optional tasks. Dynamic injection supports human tasks and the human-review task of a bank-document `AGENT_THEN_HUMAN` step. Dynamic autonomous agent tasks and dependencies among injected tasks still need a richer model.
7. Add Kafka, evidence storage, observability, recovery/load testing, CI/CD, and the remaining service boundaries from the [development plan](development-plan.md). Authentication and CI/CD were explicitly deferred for the first slice.
